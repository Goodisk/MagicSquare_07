## `.cursorrules` vs `.cursor/rules/*.mdc`

### `.cursorrules` — 구 방식 (권장하지 않음)

- 프로젝트 루트의 단일 파일
- 모든 규칙이 한 파일에 혼재
- 파일이 길어질수록 AI가 핵심 규칙을 놓칠 확률이 높아짐
- 파일 유형별 선택적 적용 불가능

### `.cursor/rules/*.mdc` — 현재 방식 (권장)

- `.cursor/rules/` 디렉토리 아래 파일별로 분리
- 각 파일에 YAML frontmatter로 적용 범위 제어
- `alwaysApply: true` — 모든 세션에 항상 포함
- `globs: **/*.py` — 해당 파일이 열릴 때만 포함
- 규칙이 짧고 집중적일수록 AI가 정확하게 따름

**MagicSquare 프로젝트는 `.cursor/rules/*.mdc` 방식을 선택해야 합니다.**
이 프로젝트의 규칙은 성격이 세 가지로 명확히 다르기 때문입니다.

- 항상 지켜야 할 프로세스 규칙 (TDD 흐름)
- Python 코드에만 적용할 스타일 규칙
- 테스트 파일에만 적용할 품질 규칙

## MagicSquare용 규칙 파일 분할 설계

### 파일 구조

```text
.cursor/rules/
  01.tdd-process.mdc       ← 항상 적용 (프로세스 절대 규칙)
  02.python-style.mdc      ← **/*.py 파일에 적용
  03.ecb-architecture.mdc  ← src/**/*.py 파일에 적용
  04.test-quality.mdc      ← tests/**/*.py 파일에 적용
```

### 각 파일의 역할과 frontmatter

#### `01.tdd-process.mdc` — `alwaysApply: true`

- RED 없이 구현 금지
- 테스트 약화 금지 (assert 완화, `pass` 대체 등 구체적 예시 포함)
- Dual-Track 브랜치 흐름 정의
- 커밋 메시지 컨벤션 (`[RED]`, `[GREEN]`, `[REFACTOR]`)

#### `02.python-style.mdc` — `globs: **/*.py`

- Python 3.13 문법 (X | Y 타입 표기, match/case)
- 모든 함수에 type hints 필수
- PEP8 네이밍 테이블
- `print()` 금지 → `logging` 모듈 대체

#### `03.ecb-architecture.mdc` — `globs: src/**/*.py`

- Entity / Control / Boundary 레이어 디렉토리 매핑
- 의존 방향 강제 (Boundary → Control → Entity, 역방향 금지)
- 이 프로젝트의 구체적 매핑 예시
- 레이어별 금지 사항

#### `04.test-quality.mdc` — `globs: tests/**/*.py`

- AAA 패턴 필수 (주석 명시)
- 테스트 함수명 컨벤션 (`test_<대상>_<조건>_<기대결과>`)
- 하나의 테스트 = 하나의 동작 검증
- 테스트 약화 패턴 금지 예시
- conftest.py fixture 사용 가이드

### 설계 원칙 요약

| 규칙 파일 | 적용 범위 | 핵심 이유 |
| --- | --- | --- |
| `01.tdd-process` | 항상 | 프로세스는 코드 외부에서도 작동해야 함 |
| `02.python-style` | `**/*.py` | 구현/테스트 파일 모두에 스타일 적용 |
| `03.ecb-architecture` | `src/**/*.py` | 프로덕션 코드에만 레이어 규칙 적용 |
| `04.test-quality` | `tests/**/*.py` | 테스트 파일에 특화된 품질 기준 분리 |

**Cursor:**

Cursor/VSCode의 markdownlint가 이미 삭제된 파일의 진단 정보를 메모리에 캐시해서 그렇습니다.

`Ctrl + Shift + P` → **Developer: Reload Window** 를 실행하면 linter가 재시작되면서 삭제된 파일들의 경고가 모두 사라집니다.
